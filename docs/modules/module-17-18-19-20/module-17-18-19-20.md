# Module 17 — Sharing, Emergency Access, Notifications & Privacy/Security

> **MVP:** Core privacy, security, authorization, consent/audit foundations.
> **POST-MVP:** Sharing links, Emergency Card, medication reminders and advanced notification channels.
* We are clubbing modules 17, 18, 19, and 20 together. 

Implement this consolidated module within the existing Prescriptionly modular monolith, following all architecture, strict TypeScript, validation, audit/provenance, frontend, API, background-processing, and testing conventions established in Modules 0–16.

## 1. Privacy & Security Foundation

This part is mandatory for MVP.

Implement/enforce:

* patient ownership and least-privilege authorization across all medical data
* strong access-control policies at service/API boundaries
* secure session/device handling integrated with authentication
* encryption strategy for sensitive data/files in transit and at rest where infrastructure supports it
* security-sensitive audit events
* consent records where access/disclosure requires consent
* data export/deletion/account controls consistent with existing retention/audit rules
* prevention of cross-user/profile data leakage
* appropriately scoped administrative/support access

Never build an `admin can see everything` default.

Do not claim HIPAA, GDPR, or other jurisdictional compliance merely because controls exist. Actual obligations depend on deployment, geography, product role and legal review.

## 2. Sharing & Consent

Post-MVP feature built on the security foundation.

Allow patients to share **explicitly selected scopes**, never the entire wallet implicitly.

Example:

```text
Current medications     ✓
Medication history      ✓
Documents               ✗
Prescription originals  ✗
Symptoms                ✗
```

Support:

* selected patient/profile
* included data categories/date scope
* expiration
* revocation
* recipient/share-link access as designed
* creation/access/revocation audit trail
* immutable record of what scope/version was shared

Critical cases:

* forwarded link
* expired/revoked access
* wallet changes after sharing
* recipient downloads a copy
* sharing the wrong patient profile
* unauthorized guessing/reuse of tokens

Use cryptographically secure, non-predictable tokens and never expose raw internal IDs as access credentials.

## 3. Emergency Card

Post-MVP.

Emergency access must expose a **separate deliberately selected dataset**, not the normal wallet.

Potential fields:

* identity information intentionally selected
* emergency contacts
* selected current medications
* allergies
* other explicitly approved emergency information

The user controls what appears.

Design optional QR/link access so:

```text
easy emergency access
≠
unrestricted wallet access
```

Revocation/update behavior and access auditing must be defined. Never expose documents, medication history, or other sensitive information merely because it exists in the wallet.

## 4. Notifications & Reminders

Post-MVP except essential security/system notifications where required.

Support a reusable notification framework for:

* medication reminders
* document/OCR processing completion
* export completion/failure
* sharing/security/account events
* future system notifications

Include:

* notification type/status
* user preferences
* delivery channel abstraction
* timezone
* quiet hours where applicable
* retry/idempotency where delivery is asynchronous

Critical medication rule:

```text
Reminder sent
≠
Medication taken
```

Never automatically create a medication event because a reminder fired.

Ignored reminders must not automatically become `skipped` doses. Only deliberate user activity can create/update actual medication-use records.

## Cross-cutting rules

* Consent must be explicit, scoped, revocable where applicable and auditable.
* Patient/profile ownership must be validated for every operation.
* Never silently broaden access because new wallet data was added.
* Sharing/export/emergency access must preserve distinctions between confirmed, patient-reported and unverified information.
* Security-sensitive tokens/secrets must not be stored or logged in plaintext where avoidable.
* Prevent sensitive medical information from leaking through URLs, logs, analytics, errors or notification text.
* Use existing Audit/Provenance and Background Processing modules rather than duplicating them.
* Keep notification providers, sharing mechanisms and security infrastructure replaceable behind typed interfaces.

## Scope control

Do not add:

* doctor/clinician portals
* hospital integrations
* family/dependent delegation
* pharmacy access
* public medical profiles
* unrestricted permanent share links
* compliance certification claims

unless separately specified.

Implement only necessary Prisma changes, backend services/routes/policies, frontend flows/settings, token/consent models, notification abstractions, audit integration, background jobs and tests.

Test especially authorization boundaries, token expiration/revocation, wrong-profile access, consent scope, information leakage, reminder/event separation, and Emergency Card data isolation.

`summary/module-17-18-19-20-summary.md`

Document implemented security foundations, sharing/consent model, Emergency Card design, notifications architecture, schema/API changes, tests, security limitations/TODOs, and clearly identify which functionality is **MVP versus post-MVP**.
